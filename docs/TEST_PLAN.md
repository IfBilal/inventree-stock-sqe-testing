# TEST PLAN — InvenTree Stock Module (Add Stock / Remove Stock)
Version history is at the end. This is a living document: it is updated at each phase gate.

## 1. Purpose and scope
Verify the quality of the Stock adjustment workflows of InvenTree 1.8.0 dev (commit `1f51dfe64bf4717fd95df51f1055ffb7a991a01d`) as defined in `docs/TEST_BASIS.md`.
- **In scope:** WF-A Add stock, WF-B Remove stock; roles `stock_manager` and `stock_viewer`; API `/api/stock/add/`, `/api/stock/remove/`, read-backs `GET /api/stock/{id}/` and tracking history; browser stock actions; BR-1..BR-4; FR-01..FR-11.
- **Out of scope:** transfer/count/serialization workflows, purchase/sales/build orders, plugins, multi-node/Postgres behaviour, email, mobile apps, load beyond the chosen operation.
- **Items under test:** `stock/serializers.py`, `stock/models.py`, `stock/api.py` (function list in TEST_BASIS §7), the React stock dialogs, the HTTP API.

## 2. Test approach by risk level
Defined in `docs/RISK_REGISTER.md` (level → technique/depth). Summary:
| Level | Test levels | Techniques |
|---|---|---|
| Critical (PR-01) | Unit, API, E2E, mutation, CI gate | EP, 3-point BVA, decision table, state transition, MCC, MC/DC |
| High (PR-03,04,06,07,10, PJ-01..03) | Unit/API with read-back, dependency audit | EP, BVA, decision table, recovery test |
| Medium (PR-02,05,08,09) | API/E2E/tool-based | access matrix, k6, Lighthouse + axe |

Levels (from the project statement): Unit (pytest + coverage.py, 100% statement and branch of in-scope logic), API/integration (pytest + requests, generated EP/BVA data), Browser E2E (Playwright, 6 use cases × flows), usability and accessibility (Playwright, Lighthouse, axe-core), security (access matrix, ZAP passive, pip-audit), performance and recovery (k6, test-double recovery), static analysis (SonarQube), mutation (mutmut + custom operators), CI (GitHub Actions).

## 7. Entry, exit, suspension, resumption criteria
**Entry (per level):** baseline reset reproducible; server answers `/api/`; seed counts match; previous phase gate passed.
**Exit (release) criteria** — exactly three; they are also the release criteria (actual vs target in the completion report):
| ID | Category | Criterion (measurable) | Target | Tied to risk |
|---|---|---|---|---|
| EC-1 | Functional | All own business-rule tests pass on the fixed build, 0 open Critical/High defects, and 100% statement + branch coverage of the in-scope business logic (uncovered lines justified) | 100% pass, 0 open C/H, 100%/100% | **PR-01 (Critical)**, PR-03, PR-04 |
| EC-2 | Security | All access-matrix decisions (≥ 4, ≥ 1 allowed, ≥ 1 denied) observed = expected, and 0 unresolved High/Critical findings in the audited dependency set | 100% decisions correct, 0 High/Critical | **PR-02**, PR-10 |
| EC-3 | Performance | For the chosen operation at 5 users: p95 ≤ limit and unexpected failures ≤ limit (limits declared in `docs/PERF_TARGETS.md` before measuring) | p95 ≤ declared ms, failures ≤ declared % | PR-08 (and PR-01 repeated requests) |
CI quality-gate thresholds (coverage, mutation score, Sonar) are separate and justified in Phase 12.
**Suspension:** server cannot start or seed differs from baseline; CI cannot run; > 3 blocker defects in the same area. **Resumption:** environment restored via `scripts/reset.sh`, seed check passes, blocker defects triaged.
